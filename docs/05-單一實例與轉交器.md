# 單一實例與轉交器

> 這是 [README](../README.md) 的分冊，講的是「為什麼這樣做」（決策與踩過的坑）。程式在哪裡，看 [專案架構路徑](../專案架構路徑.md)。

## 單一實例是怎麼做的

第二個行程啟動後，會先透過 Windows 具名管道（`QLocalSocket`）試著連上既有實例：

- **連得上** → 把路徑送過去、把對方的視窗叫到前景，然後自己結束，不開視窗。
- **連不上** → 自己就是第一個實例，改當監聽端。

這個探測不會拖慢正常啟動：沒有實例在跑時具名管道會**立刻**回報失敗（實測
0.1～0.5 ms），不會等到逾時。

轉交本身的成本也很低，實測（扣掉量測工具本身的開銷）：

| 關聯指向 | 雙擊第二個檔案到分頁出現 |
|---|---|
| 原生轉交器（`MarkdownOpen.exe`） | **約 12 ms**（量測地板本身就 13 ms） |
| 資料夾版本體 | 約 172 ms |
| 單一 exe 本體 | 約 1,112 ms |

（2026-09 以 `tools/benchmark_handoff.py` 重測，各 8 次中位數。）

單一 exe 慢的原因和冷啟動一樣——即使只是要送一個路徑然後結束，也得先把整包
解壓到 `%TEMP%`。**常用檔案關聯的話，資料夾版的差距在這裡比冷啟動更有感。**

實作上有兩個容易踩到的點，都寫在 `app/single_instance.py` 的註解裡：

1. **不要用 `waitForBytesWritten()`**。Windows 的 `QLocalSocket` 上 `flush()` 不
   保證清空待寫緩衝區，而 `bytesWritten` 訊號在這種小量寫入後不會可靠地再發一
   次，於是它會一路空等到逾時——單這一項就讓每次雙擊多花整整一秒。改成交給
   `disconnectFromServer()`：它會先送完待寫資料再關閉。
2. **收方要能處理「資料還沒進緩衝區就已斷線」**。送方寫完立刻要求關閉，
   `readyRead` 與 `disconnected` 誰先到並不固定。少了補讀那一步會讀到空字串，
   症狀是「分頁開出來卻是空白」。

> 量測時注意：把送方和收方寫在同一個行程裡會失真——送方的 `waitFor*` 會鎖住事
> 件迴圈，收方根本沒機會處理連線。要用兩個真正的行程量。

### 多選是 N 條轉交，不是一次

在檔案總管多選 `.md` 再按開啟時，Windows **一律「每個檔案叫一次開啟指令」**。
這不是我們能改的：拿檔案總管自己走的那條路（`IShellFolder::GetUIObjectOf`
取 `IContextMenu`，再 `InvokeCommand("open")`）對 3 個檔案實測五種註冊組合——
`%1` 不加 `MultiSelectModel`、`%1`＋`Player`、`%*`＋`Player`、`%1 %*`＋`Player`、
`%1`＋`Document`——全部都是叫用 3 次、每次拿到 1 個路徑，`%*` 甚至一個都拿不到。
要一次收下多個檔案只剩 COM 的 `DropTarget`／`ExecuteCommand` 處理常式那條路，
為此養一個 COM 伺服器不划算。

所以十個檔案＝十個轉交器行程、十條轉交訊息，在大約 150 ms 內陸續進來。
每一條都當成獨立開檔的話就是十次完整開檔（上面那個 3.4 秒、閃 63 次的數字）。
`window_manager.route_external_open` 因此認「連發」：一條路徑進來時若距離上一條
**處理完**不到 `BURST_SECONDS`（0.4 秒），就當成同一批，只建延後分頁、不切過去；
每處理完一條就重新計時，長串不會被拆開。

三件容易寫錯的事：

1. **計時要在「做完」之後蓋章，不是「開始處理」時。** 渲染是同步的，一份大文件
   的首屏可能就吃掉整個窗口；在開始前蓋章的話，第一個檔案越大越容易被判成不同
   批——正好在最需要批次的時候安靜失效。
2. **冷啟動要自己種下第一批。** 沒有實例在跑時，第一個檔案是轉交器放在命令列上、
   由本行程自己開的，沒有經過 `route_external_open`。不補一句 `note_batch_started`
   的話，使用者選的第二個檔案會被當成新的一批而切過去——十個檔案開起來停在
   第二個，還多付一次渲染與一次搶前景。
3. **窗口誤判時不能讓檔案「消失」。** 同一批的後續不切分頁，但視窗若不在前面
   仍要把它叫出來；否則使用者按了開啟卻什麼都沒發生，和「程式沒反應」無法區分。

分頁的排列順序由這 N 個行程搶管道的先後決定，**刻意不排序**：檔案總管的檢視
順序可能是日期或大小，抵達順序（≈ 叫用順序 ≈ 使用者看到的順序）反而是最接近的
近似，照檔名排序才是錯的。

> `MultipleInvokePromptMinimum`（檔案總管對「一次開太多檔案」的提示，預設 15）
> 是整個 shell 的設定，**刻意不碰**：那是使用者誤選兩百個檔案時唯一的保護，
> 一個閱讀器沒有立場代替他改；而且我們自己也需要那道上限——延後分頁省的是讀檔
> 與渲染，每個分頁仍然要建一個閱讀區元件。

## 原生轉交器（MarkdownOpen.exe）

上面的轉交成本還能再砍。轉交那 170 ms／1064 ms 幾乎全花在「載入 python313.dll
與整套 PyQt6」——即使那個行程只是要把路徑送出去就結束。`src_cpp/md_open/` 是
一支 38 KB 的原生 Win32 程式，只做三件事：

1. 試著連上具名管道（Qt 的 `QLocalServer` 在 Windows 上就是 `\\.\pipe\<名稱>`
   的位元組模式管道，用 `CreateFile` + `WriteFile` 就能當它的客戶端，不需要 Qt）。
2. 連得上就把路徑送過去、結束；連不上就啟動本體，參數原封不動傳過去。
3. 用具名互斥鎖排隊：一次選取多個 `.md` 按 Enter 時，第一個負責帶起本體，
   其餘等管道出現後轉交，不會各自開一個視窗。

實測（`tools/benchmark_handoff.py`，各 10 次取最小值，量測工具本身的
地板 9 ms 已列出供對照）：

| 動作 | 直接啟動本體 | 經原生轉交器 |
|---|---|---|
| 已開著時再雙擊（資料夾版） | 169 ms | **10 ms** |
| 已開著時再雙擊（單一 exe） | 1,046 ms | **9 ms** |
| 冷啟動到視窗出現（資料夾版） | 622 ms | 634 ms（+22～26 ms） |

冷啟動多出的 22～26 ms 是多開一個行程的固定成本；轉交器會在本體的管道
開起來後（早於視窗出現）就退場，不會殘留。

把檔案關聯指向轉交器就能吃到這個加速（`build.ps1` 完成訊息也會提示這個路徑）：

```bash
py -3.13 tools/install_association.py --target "D:\software\Customize-Open-File\md\dist\MarkdownReader-onedir\MarkdownOpen.exe"
```

轉交器由 `build.ps1` 的第 5 步自動編譯（需要 MSYS2 UCRT64 的 g++；沒有就
略過，主程式不受影響）。要在 VS Code／Cursor 裡改它：`.vscode/` 已設好
IntelliSense（對準 UCRT64 g++）、`Ctrl+Shift+B` 建置（旗標與 build.ps1 一致），
以及 `F5` 用 gdb 除錯（會另編一份帶符號、未 strip 的 `MarkdownOpen-debug.exe`
——發佈版的 `-s` 會把符號拔光，直接除錯發佈版什麼都看不到）。圖示是內嵌的必要品：關聯腳本拿「目標 exe 的第 0 個
圖示」當 `.md` 的檔案圖示，沒有它所有 `.md` 都會變白紙。

幾個實作上的防呆，都寫在 `main.cpp` 的註解裡：

- **等待以本體行程的狀態為界，不是死板的時鐘。** 本體啟動就當機 -> 立刻放棄
  （實測 138 ms）；本體 GUI 起來了卻始終沒開管道（`listen()` 失敗）-> 寬限
  4 秒後放棄（實測 5.1 s），不會握著排隊鎖空等滿 15 秒。
- **管道名稱＝基底名稱＋登入工作階段編號，兩邊各算一次，靠測試鎖住一致性**：
  具名管道是整台機器共用的，沒有互斥鎖那種 `Local\` 前綴可用。兩個使用者同時
  登入時，後登入的人雙擊 `.md`，路徑會被送進前一個人的視窗——在他看不到的桌面
  上開了分頁，自己這邊什麼都沒發生。所以 Python 端（`config.IPC_SERVER_NAME`）
  與轉交器（`main.cpp` 的 `pipe_path()`）都把 `ProcessIdToSessionId` 的結果接在
  基底名稱後面：`MarkdownReader.SingleInstance.<工作階段>`。用工作階段編號而不是
  使用者名稱，是因為同一個人從主控台與遠端桌面同時登入也是兩個桌面，各自一個實例
  才對；而且編號是純數字，不必煩惱使用者名稱裡的中文與空白在兩邊的編碼。
  （`config.py` 的註解以前寫「要含使用者名稱」，但名稱其實什麼都沒含，排查多使用者
  互搶時會被引到錯的方向。）`tools/smoke_test.py` 比對兩邊的基底名稱與算法——改到
  不同步立刻紅燈，否則不會有任何錯誤訊息，只是安靜退化成每個檔案開一個視窗。
  環境變數 `MDREADER_PIPE_NAME` 可整個換掉名稱，Python 與轉交器都讀：回歸測試靠它
  讓自己開的本體與轉交器走專屬管道，不碰你正在用的閱讀器。
- **送出前呼叫 `AllowSetForegroundWindow`**：前景權限在剛被雙擊的行程手上，
  不轉讓的話既有視窗只能在工作列閃爍。
- **管道「存在但忙」要重試，不能一次放棄**：這個狀態代表本體一定活著（管道會
  隨行程消失），只是還沒回到事件迴圈。放棄的代價是誤判「沒有實例」再生一個
  完整的本體行程（600 ms 起跳），所以忙碌重試的上限放到 3 秒。
- **收方不能在 socket 的訊號裡直接做重活**（這是 Python 端 `single_instance.py`
  的相對修正）：`readyRead` 來自 Qt 管道讀取回呼，在那個框架裡直接
  「拆 socket → 開分頁 → 渲染大檔」，會與其他排隊連線的管道回呼交錯，實測
  三條連線背靠背時必定以 `0xC0000005` 崩潰在原生層。`deliver()` 改用
  `QTimer.singleShot(0, ...)` 把派送推回事件迴圈。`tools/smoke_test.py` 有
  對應的回歸測試（掛起本體 + 三連發）。
