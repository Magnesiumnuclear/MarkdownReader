# 分頁與多視窗

> 這是 [README](../README.md) 的分冊，講的是「為什麼這樣做」（決策與踩過的坑）。程式在哪裡，看 [專案架構路徑](../專案架構路徑.md)。

## 什麼情況會開新分頁

| 動作 | 結果 |
|------|------|
| 在檔案總管雙擊 `.md` | 送給既有視窗開成新分頁；沒有視窗在跑時才開新程式 |
| 點文件裡的本機 `.md` 連結 | 開成新分頁（原本那篇留在原分頁，隨時切得回去） |
| `Ctrl + O` 選檔、拖放檔案 | 開成新分頁 |
| `Ctrl + T` 或分頁列「＋」的主區域 | 開一個空白分頁（可直接貼上原始碼） |
| 分頁列「＋」右側的箭頭 | 展開選單選「開啟檔案…」 |

同一個檔案不會重複開：已經開著時直接切過去，不會多出一個一樣的分頁。

### 「＋」是一顆按鈕、兩個功能

主區域開新分頁，右側箭頭在按鈕正下方展開選單，裡面是「開啟檔案…」。

這同時修掉一個名實不符：改版前「＋」的提示寫著「開新分頁 (Ctrl+T)」，按下去
跳出來的卻是開檔對話框（`newTabRequested` 直接接到 `open_dialog`），而真正開空白
分頁的只有 Ctrl+T。現在提示、主區域行為與 Ctrl+T 三者一致。

實作上沒有用 `QToolButton` 的 `MenuButtonPopup`：那個模式的箭頭由 Qt 樣式自己畫，
違反本專案「圖示一律來自 `assets/icons/*.svg` 並隨主題變色」的規範。改成
`SplitIconButton` 自己畫箭頭（沿用 `icons.pixmap` 的著色與快取），以 x 座標切一刀
決定點到的是主區域還是展開區。選單是空的時候完全退化成一般 `IconButton`。

### 空白分頁可以直接貼上 Markdown 原始碼

在空白分頁按 `Ctrl+V`，剪貼簿裡的 Markdown 原始碼會立刻排版顯示；再貼一次會覆蓋。
這是**唯讀的貼上即渲染**，不是編輯器——本程式的閱讀區始終是唯讀的 `QTextBrowser`。

幾個刻意的邊界：

- **只對沒有檔案路徑的分頁生效**。正在讀某個檔案時按 `Ctrl+V` 不會把它換掉。
- **焦點在搜尋框時，`Ctrl+V` 仍然是搜尋框的貼上**。這個捷徑掛在視窗上，預設會
  先攔下按鍵；偵測到搜尋框有焦點就把貼上轉交回去，否則「複製一段字、貼進搜尋框」
  會整個失效。
- **不會被工作階段還原**。貼上的內容沒有路徑，而還原機制存的本來就是路徑清單
  （`_save_session` 的 `if tab.path`），所以這件事零改動就成立。

貼上的內容需要一份合成的 `DocumentMeta`（`build_html` 靠 `meta is None` 判斷要畫
歡迎頁還是文件），見 `document.meta_for_pasted`。分頁標題會變成「貼上的內容」。

分頁列**永遠顯示**（含單一分頁）——隱藏的話單開一個 .md 就沒有分頁可以抓，
永遠拖不去別的視窗合併。分頁太多時可以在分頁列上橫向捲動，中鍵點分頁也能關閉。

### 關閉鈕是疊上去的，不佔版面

未選取的分頁平常不顯示叉叉（整列都是叉叉太吵），滑鼠移上去才出現。叉叉若排在
版面裡，出現的那一刻分頁就會**寬出 24px**，右邊所有分頁跟著往右跳——手還在移動
的時候版面在動，很難瞄準，而且滑鼠一離開又縮回去，整列會抖。

所以關閉鈕改成**絕對定位、疊在檔名右端**：分頁寬度從此只由檔名決定，滑鼠怎麼動
都不變。代價是叉叉會蓋到長檔名的尾巴，因此底下鋪一條與分頁同色的襯底——右段實色
把字擋掉，左段漸層淡出接回分頁底色，不會出現一條突兀的硬邊。

襯底的顏色要**先合成再寫進 QSS**。分頁有兩種底色：未選取被滑鼠指著時是半透明的
`hover_bg` 疊在分頁列的 `surface` 上，選取中則是不透明的 `window_bg`。QSS 算不出
「半透明疊在某個底色上等於什麼顏色」，所以 `styles._blend()` 先算好實色再代入樣板。
漸層的起點也不能寫 `transparent`——Qt 在非預乘的 RGBA 空間內插，透明黑漸變到不透明
白會從灰色走過去，淺色主題上會看到一條髒邊；起點必須是「同色但 alpha=0」。

三個踩過的坑，都有回歸測試釘住：

1. **疊放順序**：襯底要在檔名**之上**、關閉鈕之下。寫成 `lower()` 會把襯底壓到
   檔名底下，看起來就是「叉叉和字糊在一起」——實測叉叉在合成畫面裡只剩 1 個像素。
2. **`resizeEvent` 不能用 `isVisible()` 當守衛**。`isVisible()` 問的是「現在畫得到
   嗎」，視窗還沒 `show()` 之前一律是 `False`——而分頁拿到最終寬度的那一次 resize
   正好發生在那個時候。守衛擋掉之後覆蓋層就停在建構當下的 sizeHint 寬度（實測 100，
   實際分頁 133），叉叉會落在檔名中間。
3. **覆蓋層要讓開框線**：上緣 2px 是 `border-top`（選取中的分頁那條是強調色），
   右緣 1px 是 `border-right`。子元件畫在框線之上，鋪過去會把兩條線蓋掉。

> 測遮蓋效果時有個陷阱：色票裡 `icon_active` 和 `text` 是同一個色碼（`#1f2328`），
> 直接數「襯底範圍內的檔名色像素」會把叉叉自己算進去。測試因此先把叉叉收起來再量。

## 分頁拖曳（比照瀏覽器）

| 手勢 | 結果 |
|------|------|
| 在分頁列內左右拖 | 即時重排，跨過鄰居的中心點就交換位置；同時標出會插進哪條縫 |
| 拖出分頁列（任一方向約 48px）再放開 | **拆分**：該分頁變成一個新視窗，出現在放開的位置 |
| 拖到**另一個視窗**的分頁列上放開 | **合併**：插進游標所指的位置，並切換到該分頁 |

拖出分頁列後會有一個**半透明的分頁縮影**跟著游標，**按下時抓的那一點會一直
待在游標底下**（比照瀏覽器）——抓分頁左緣就從左緣拖著走，抓右緣就從右緣。
縮影下方的徽章即時預告放開會發生什麼：**合併**（強調色實心）、
**拆分為新視窗**（描邊）、**無動作**（灰）。此時縮影會**變得更透明**
（0.9 → 0.45）——相對跟隨讓縮影蓋在游標正下方，而那正是指示線所在的位置，
不讓路的話抓分頁中央拖去合併時指示線會被完全遮住。預告、指示線與放開時的實際
決策走同一段程式（同一個 `drop_target_at` 結果），不會說一套做一套。
放開點的判定規則：

- 放開在**本列上** → 純重排。
- 放開在**容忍帶內（超出列不到 48px）** → 只允許合併：游標下有別的視窗的
  分頁列就合併，沒有就不動作——手滑超出幾個像素不會噴出一個新視窗。
  這條也讓「兩個視窗相鄰、分頁列同高」時橫向拖過去能直接合併。
- 放開在**容忍帶外** → 有目標就合併，沒有就拆分成新視窗。

### 插入位置指示（會插在哪兩個之間）

拖曳時分頁條上會出現一個**強調色的 I 形指示**：一條線，上下各扣一個三角帽。
**列內排序與跨視窗合併都會出現**，但兩者決定位置的方式不同。

**只有一條規則**：游標此刻落在被拖分頁的哪一半，就畫那一側的緣。

| 游標相對被拖分頁中心 | 指示線 |
|---|---|
| 在右半（含正中心） | 畫這一格的**右**緣 |
| 在左半 | 畫這一格的**左**緣 |

判斷的是游標**此刻**的位置，不是相對按下點。差別只在「往右拖到底再往回晃」：
若比對按下點，會一直停在右緣——只表達「你從起點往右移過」，游標明明已經往回也
不翻邊。改看被拖分頁的中心後，游標一越過中心就翻成左緣，貼著它當下在哪。使用者
要的正是後者：以滑鼠當下的相對位置判左右。

因為列內即時重排會把被拖分頁一路挪到游標底下，指示線本來就貼在它的邊上；這條
規則只決定貼哪一邊。用被拖分頁自己的中心當界，抓取點落在左半或右半都不影響，
純看游標現在偏哪邊。有一條回歸測試專門釘這件事：抓左邊緣按下、往右移到仍在中心
左側的位置，斷言畫的是**左**緣（游標在左半）；換成按下點基準就會變右緣。

拖曳中一律顯示一側，不設「正中心不畫」的中性帶——那要像素精準的相等判斷（分頁寬
是偶數，中心落在兩像素之間），實際永遠不會剛好命中，只是多一個測不準的分支。正
中心歸右半。手勢還沒真的開始（沒超過 `QApplication.startDragDistance()`）時
`_drag_button` 還是 None，那時 `_on_drag_moved` 根本不會被呼叫，什麼都不畫。

> 回歸測試用「`_drag_button` 有沒有值」排除手勢還沒開始的那幾步，而不是
> 「跳過第一筆」那種看心情的規則。

**跨視窗合併：由視窗層指定索引**（`insert_index_at` 算游標落在哪條縫），不受上面的
規則影響——那是插進**別人的**順序裡，沒有「原位」可言。

> 定位讀的是 `buttons[i].x()`，所以 `_move_button` 重排後要立刻 `activate()` 版面。
> `insertWidget` 只是排程一次 `LayoutRequest`，沒跑完之前每顆按鈕的 `x()` 都還是舊
> 槽位的值，線會畫在隔壁那條縫上，而且要等下一次滑鼠移動才更正——使用者跨過一個
> 鄰居就停手時，線會一直停在錯的地方。

三角帽不是裝飾：分頁之間本來就有一條 1px 的分隔線，純粹加粗那條線在深色主題下
很難分辨是「新東西」還是分頁自己的邊框；上下兩端各張開一個比線寬四倍的三角，
形狀就不可能和任何既有的邊框混淆。線走 QSS、三角帽走
`assets/icons/insert_cap_*.svg`（同一份向量圖換色跟著主題走），符合專案
「圖示一律來自 SVG 檔、外觀集中在 styles.py」的規範。整塊是分頁條上的
**覆蓋層**、不進版面——進版面的話每次移動都會把分頁擠開重排。

兩個邊界情況：

- 最左邊那條縫的座標是 0，指示線因此有一半落在分頁條外被裁掉。這是刻意的：
  它的職責是說「插在哪」，寧可帽子少一半，也不要為了完整顯示而把線挪進第一個
  分頁裡、指到錯的縫。
- 游標離開本列但還在容忍帶內時，本列**不畫**自己的線。那時重排仍在進行，
  但游標可能正停在別的視窗的分頁列上、那邊已經畫了一條；兩條同時亮，
  使用者就無從知道放開會插到哪一個。

**這個功能曾經完全看不見。** 樣式規則寫在拖曳幽靈的那份 QSS 裡（幽靈是獨立的
頂層視窗，自己 `setStyleSheet` 一份），主視窗的子元件根本吃不到，
`isVisible()` 一路回 True 卻一個像素都沒畫，而當時的回歸測試只問 isVisible，
全綠。現在的測試改成量**指示線那一欄每一列有多寬**：中間那列必須等於線寬、
上下兩列必須更寬。線、上帽、下帽三者因此可以各自被單獨打破——少了線中間歸零，
少了帽子該端縮回線寬，樣式再搬錯地方也會紅。

細節與取捨：

- 所有視窗都在**同一個行程**裡（瀏覽器模型）。拆分／合併是把分頁物件直接
  搬過去——已渲染的內容、返回歷史、捲動位置都原封不動，不會重新讀檔。
- 合併時目標視窗的主題可能不同，搬過去的分頁會用目標視窗的主題重新渲染，
  不會出現「深色視窗裡有一頁是淺色」。
- 空掉的來源視窗自動關閉；最後一個視窗關閉時程式結束。
- 單一分頁拖到空白處不做事（那等於拖整個視窗，標題列本來就能做）。
- 雙擊 `.md` 轉交進來的檔案，開在**最後作用中**的那個視窗。
- 「還原上次分頁」目前只記住**最後關閉**的那個視窗的分頁（多視窗的完整
  還原是已知限制，見 [README](../README.md) 的「已知限制」）。

實作上最容易踩的三個坑寫在 `app/tab_bar.py` 的模組與類別註解：

1. 按下分頁會觸發 activate → set_tabs，若在拖曳中重建按鈕，被按住的那顆會
   被銷毀、滑鼠抓取跟著消失。set_tabs 因此在結構沒變時只就地更新樣式。
2. 撕下狀態不能只靠移動事件設定，**放開時要用放開點重新判定**。兩個視窗
   相鄰（間距小於容忍帶）時，游標已經在對方分頁列上、卻還沒離開本列的
   容忍帶——只信移動事件設的狀態，放開就什麼都不做。
3. 縮影相對跟隨的代價是**它必然蓋住游標**，而合併目標原本是用
   `QApplication.topLevelAt` 決定的。Qt 在 Windows 走
   `ChildWindowFromPointEx(..., CWP_SKIPINVISIBLE)`，只跳過隱藏的視窗、
   不跳過 `WS_EX_TRANSPARENT`，所以它會回傳縮影。實測 60 個落在縮影內的
   點，`topLevelAt` 100% 抓到縮影。

### 為什麼合併的命中測試改用原生 `WindowFromPoint`

`topLevelAt` 抓到縮影**不會**讓分頁併到縮影上——縮影既不是來源視窗也不在
候選清單裡，`drop_target_at` 的堆疊判定會整段失效，**安靜地退回「最後作用
優先」的幾何掃描**。後果是分頁併進一個被完全遮住、使用者根本看不到的視窗，
而且因為幾何掃描有時剛好猜對，症狀是時好時壞。

`win32.top_level_hwnd_at()` 改用 `WindowFromPoint` + `GetAncestor(GA_ROOT)`：
它是唯一會跳過 `WS_EX_TRANSPARENT` 的原生點查詢。實測同樣 60 個點，
0% 抓到縮影、100% 答出底下的視窗。成本比其他可行方案低兩個數量級
（`QApplication.widgetAt` 挖 1×1 洞在 dpr 1.5 下只有一半準確率；
`hide()`/`show()` 或 `setMask` 打洞各要 2.3–2.4 ms，跑在每個滑鼠移動事件上
是 125 Hz 預算的三成）。

這也讓 `Qt.WindowType.WindowTransparentForInput` 從「視覺選擇」升級為
**功能相依**：它是那個 `WS_EX_TRANSPARENT` 的唯一來源，只留
`WA_TransparentForMouseEvents` 產生不出這個 exstyle，拿掉之後連
`WindowFromPoint` 也會抓到縮影。

邏輯座標要換成原生像素才能問 `WindowFromPoint`。不能全域乘一個
`devicePixelRatio`：Qt 的高 DPI 換算是「每個螢幕各自縮放、原點守恆」，
多螢幕不同縮放時只有取點所在那個螢幕的原點與比例才會對。換算完還會回頭
檢查解出來的視窗是否真的含這個點——若在某種多螢幕組合下失準，就退回既有的
幾何掃描，寧可退化成修正前的行為，也不拿一個錯的視窗當答案。

## 邊緣縮放器握著別的視窗的元件（間歇性硬崩潰）

無邊框視窗的邊緣縮放靠 `FramelessResizer`：事件過濾器裝在視窗與所有子元件上，
另外用 `_drag_controls` 記著「縮放要讓開」的捲軸（游標在捲軸上時感應寬度縮到 4px）。
那份名單是**快照**，分頁增減後由 `_refresh_resizer_targets()` 重新登記。

`take_tab()`（把分頁交給別的視窗）在「交出後視窗就空了」那條路徑上**提早
return**，跳過了重新登記。結果是：剛交出去的那個閱讀區的捲軸還留在名單裡，
而它現在屬於**收養它的那個視窗**。實測交出最後一個分頁後，六筆名單裡有兩筆
是外來的。

這不只是髒資料。收養方的視窗一關，那兩筆就是懸空指標，而命中測試長這樣：

```python
try:
    visible = widget.isVisible()      # 有 try
except RuntimeError:
    continue
alive.append(widget)
if not visible:
    continue
rect = QRect(widget.mapToGlobal(QPoint(0, 0)), widget.size())   # 沒有 try
```

`isVisible()` 有防護，但 `mapToGlobal()` 與 `size()` **在 try 外面**。物件正在被
拆掉時，前者可能還過得去、後者往更深處解參照就直接 `0xC0000005`——那不是能
`except` 的例外，是行程當場中止。這正是回歸測試裡那個間歇崩潰的堆疊指到的位置。

三處都改了：

1. `take_tab()` 的空視窗路徑補上重新登記——不讓名單髒掉。
2. `_refresh_resizer_targets()` 的名單更新不再被 `isVisible()` 擋掉。事件過濾器
   可以等 `showEvent`，但名單是正確性問題，視窗還沒顯示也要更新。
3. `_over_drag_control()` 改成**先問 `sip.isdeleted()` 再碰物件**，並剔除
   `window() is not self._window` 的外來元件；`mapToGlobal`／`size` 移進 try。
   `sip.isdeleted()` 只問包裝自己的狀態，不會解參照——用 `isVisible()` 探路
   等於先解參照再祈禱。（PyQt6 沒有 `QPointer`，`sip.isdeleted()` 是對應的工具。）

**測得到與測不到的部分要分清楚。** 前兩項與「剔除外來元件」有確定性的回歸測試
（直接量名單內容，不賭崩潰會不會發生），而且都通過反向驗證。但
「先問 sip 再碰物件」這一項**沒辦法寫確定性測試**：在 Python 裡能造出來的
「已刪除」都是 sip 知情的，`isVisible()` 會乖乖丟 `RuntimeError` 被接住，新舊
兩版行為一樣。它保護的是「C++ 端把物件連帶刪掉、sip 還沒被通知」那種情形，
造不出來也就測不到——留著是因為它嚴格更安全且零成本，不是因為有測試撐著。
