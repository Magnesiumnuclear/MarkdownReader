# 設定與語言

> 這是 [README](../README.md) 的分冊，講的是「為什麼這樣做」（決策與踩過的坑）。程式在哪裡，看 [專案架構路徑](../專案架構路徑.md)。

## 設定存在哪裡

一般模式存登錄檔 `HKCU\Software\SamHo\MarkdownReader`（`QSettings` 的原生格式）；
可攜版（exe 旁有 `portable.txt`）改存 `<exe 目錄>\data\settings.ini`。哪一種由
`app/resources.py` 的 `make_settings()` 一處決定，全專案不允許別處直接建 `QSettings`
——否則可攜模式會有一部分設定漏回登錄檔，回歸測試會掃出來。細節與為什麼用標記檔
見 [07-打包與發布.md](07-打包與發布.md) 的「可攜版為什麼要一個標記檔」。

## 錄影擷取排除（標題列的攝影機鈕）

按下後錄影、截圖、螢幕分享都擷取不到本程式的視窗，自己的螢幕照常顯示。設定存在
`window/excludeFromCapture`，不在設定面板裡（「恢復預設值」也不會動它——錄影錄到一半
按了恢復預設，視窗突然出現在錄影裡，那是最不該發生的事）。

幾個決定：

- **用 `WDA_EXCLUDEFROMCAPTURE`，舊系統退回 `WDA_MONITOR`。** 前者（Windows 10 2004 起）
  讓視窗在擷取畫面裡完全不存在；後者只能讓它變成一塊黑——仍然擋住內容，但看得出那裡
  有東西。`win32.set_capture_excluded` 一律讀回實際狀態再回傳，狀態列依結果說「已隱藏」
  或「只能變黑」。
- **沒生效就不亮。** 讀回不是那兩個值，按鈕彈回未勾、設定不寫、不推給別的視窗，狀態列
  說無法。使用者正要開始錄影，以為藏起來了其實沒有，比按了沒反應糟得多。
- **所有視窗一起，不是一個視窗一個。** 釘選是每個視窗各自的；這個不是——只藏一個視窗，
  錄影裡照樣看得到另一個視窗的內容。按下時推到 `window_manager` 的每個視窗；新開、拆分
  出來的視窗在 `showEvent` 就套上（要有原生視窗才套得上），一出現就藏好，不會在錄影裡
  閃一幀。
- **原生視窗重建時設定會掉。** 釘選退回 Qt 旗標（`setWindowFlag`）會重建原生視窗，重建後
  的 `show()` 同樣經過 `showEvent` 重套，回歸測試釘著這條。
- **拖曳分頁的縮影也藏。** 它是自己的頂層視窗，帶著分頁縮圖與檔名，一拖就會露出來。
- **已知限制**：存檔詢問、外部連結確認等 `QMessageBox`，與 Windows 原生的開檔／存檔對話框，
  都是另外的視窗，不在排除範圍內。

## 設定面板

按 `Ctrl+,` 或標題列的齒輪鈕開啟。面板會**覆蓋標題列以下的整個視窗**，是一頁
完整的設定畫面，因此每個項目都配有名稱與說明文字。標題列保持可見——無邊框視窗
需要它才能拖曳與關閉，齒輪鈕本身也是收起面板的方式之一（`Esc` 或右上角的
關閉鈕也可以）。視窗不夠高時面板會垂直捲動。

| 區塊 | 項目 | 選項 |
|------|------|------|
| 外觀 | 語言 | 繁體中文 / English / 跟隨系統（預設） |
| | 主題 | 淺色 / 深色 / 跟隨系統（預設） |
| | 字級 | 7～30 pt，與 `Ctrl` `+` / `-` / `0` 連動 |
| | 行高 | 緊湊 142% / 標準 160% / 寬鬆 188% |
| | 內文寬度 | 窄 720px / 中 900px / 不限 |
| 行為 | 檔案監看 | 存檔後自動重新渲染並保留閱讀位置 |
| | 視窗 | 釘選最上層，等同 `Ctrl+P` |
| | 狀態列 | 顯示底部檔案資訊，等同 `Ctrl+/` |
| | 外部連結 | 開啟前先跳出確認 |
| | 還原上次分頁 | 關閉時記住開著的分頁，下次啟動時還原（預設關閉） |
| 重設 | 恢復預設值 | 全部歸零，主題也回到「跟隨系統」 |

分段選擇與開關共用同一種「晶片」外觀：未選取是描邊、選取是強調色實心。

## 語言

介面語言在設定面板「外觀」區的第一列——看不懂目前介面的人，會從第一區的第一列
開始找。切換後**所有開著的視窗立刻更新**（透過 `WindowManager.broadcast_language`），
不需要重開程式。預設「跟隨系統」，取的是 Windows 的**顯示語言**
（`QLocale.uiLanguages()`）而不是地區格式——顯示語言設英文、地區設台灣的機器上，
`QLocale.name()` 會回報 `zh_TW`，那不是我們要問的問題。

字串放在 `languages/zh_TW.json` 與 `languages/en.json`，程式端一律透過
`language.t("鍵")` 取用。用 JSON 查表而不是 Qt 的 `.ts`/`.qm` 工具鏈：全部只有
一百多條字串，純文字檔看得懂 diff、改完存檔就生效，不必多養一道 `lrelease`
編譯步驟。鍵是**扁平的**（分類靠 `titleBar.` / `settings.` 這類前綴），兩份檔案
因此可以用一句 `sorted(a) == sorted(b)` 驗證對齊——回歸測試裡的「語言檔完整性」
就是這樣寫的。

**一句話一個鍵，絕不在程式碼裡拼接。** 中英語序不同（「切換到{target}主題」/
"Switch to {target} theme"），拼接出來的英文語序永遠會是錯的；全形標點
（`（）～／：·`）也一律由翻譯字串整條承載，英文用半形，那是翻譯的一部分。

實作上有四個地方值得記下來：

1. **面板上三分之二的字原本改不了。** `_add_section` / `_add_row` 建的 `QLabel`
   是區域變數，建完就丟；`IconButton` 的 tooltip 也只在建構時設一次。改成建的
   時候把「元件 → 翻譯鍵」登記起來，語言一換走訪登記表就地重設，不重建面板
   （重建會讓捲動位置歸零、晶片的勾選狀態要重同步）。
2. **有三處拿翻譯過的文案當程式邏輯用**，一翻譯就壞，都已改掉：歡迎頁判定原本
   比對產品名稱字串、忙碌提示的還原原本比對訊息前綴（改用 `_status_is_busy`
   旗標）、分頁的 `matches()` 原本比對 tooltip（改比對路徑這個穩定身分——
   翻譯讓它誤判成結構改變就會在拖曳中重建按鈕，那正是 `tab_bar.py` 開頭警告的
   崩潰類別）。
3. **Windows 會自動補標題後綴。** Qt 若發現 `windowTitle` 沒有以
   `applicationDisplayName` 結尾，就自作主張補一段 ` - <displayName>`。
   `main.py` 與 `viewer._update_titles` 的來源一旦分家，工作列會出現
   「note.md — Markdown Reader **- Markdown 閱讀器**」。兩邊同源於
   `t("app.displayName")`，回歸測試用精確標題比對把它釘住。
4. **Qt 內建元件的文字也一併處理了。** 這個專案原本從未載入 `QTranslator`，
   所以右鍵選單與訊息框按鈕一直顯示英文源字串（中文介面配英文右鍵選單）。
   現在切到中文時會載入 Qt 自己的 `qtbase_zh_TW.qm`（本來就隨 PyQt6 打包進去，
   不需要多帶任何東西）。

> **已知限制：** `QFileDialog` 在 Windows 走的是原生對話框，「開啟／取消」這些
> 按鈕的文字**永遠跟隨系統語言**，本程式控制不到。我們能控制的只有對話框標題
> 與檔案類型篩選。要一致就得改用 Qt 自繪版（`DontUseNativeDialog`），但那會
> 失去快速存取與最近使用清單，不划算。

## 系統主題

主題模式預設是 **跟隨系統**：

- 首次啟動時讀取 Windows 的「選擇您的預設應用程式模式」，直接套用對應配色。
- 之後在 Windows 切換深淺色，視窗會**即時**跟著變，不需要重開程式。
- 在設定面板選了「淺色」或「深色」就會鎖定，不再跟隨；想恢復自動就選回「跟隨系統」。
- 標題列的主題切換鈕等同於「切到另一個配色並鎖定」。

偵測優先使用 Qt 6.5+ 的 `QStyleHints.colorScheme()`（即時同步就是靠它的
`colorSchemeChanged` 訊號）；若回報 `Unknown`，才退回讀登錄檔的
`HKCU\...\Themes\Personalize\AppsUseLightTheme`。
