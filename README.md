# Markdown 閱讀器

專為 Windows 打造的輕量級 Markdown 閱讀器。雙擊 `.md` 檔案即可用 GitHub 風格排版閱讀，具備無邊框視窗、自訂標題列、多分頁、深淺色主題與釘選最上層。再雙擊其他 `.md` 會開在同一個視窗的新分頁。

---

## 功能

| 分類 | 內容 |
|------|------|
| 開檔 | 接收 Windows 傳入的命令列路徑、`Ctrl+O` 選檔、拖放檔案到視窗 |
| 排版 | GitHub 風格 CSS、程式碼語法高亮、表格、任務清單、註腳、定義清單、刪除線 |
| 視窗 | 無邊框 + 自訂標題列、拖曳移動（保留 Aero Snap）、四邊四角縮放、雙擊最大化 |
| 閱讀 | 深淺色主題切換、字級縮放、`Ctrl+F` 搜尋並高亮全部符合項（可切換區分大小寫／全字）、狀態列資訊 |
| 設定 | 覆蓋式設定面板（`Ctrl+,`）：主題模式、字級、行高、內文寬度、行為開關，一鍵恢復預設 |
| 主題 | 預設跟隨 Windows 深淺色設定並即時同步，也可手動鎖定淺色或深色 |
| 語言 | 繁體中文 / English，預設跟隨系統；切換後所有開著的視窗立刻更新 |
| 分頁 | 多分頁閱讀、中鍵關閉、分頁列可橫向捲動；可選擇記住上次開著的分頁 |
| 單一實例 | 再雙擊 `.md` 會開在既有視窗的新分頁，而不是另開一個程式 |
| 便利 | 釘選最上層、存檔後自動重載並保留閱讀位置、本機 `.md` 連結開在新分頁、點狀態列的路徑可在檔案總管中選取該檔、滑鼠移到連結上即在狀態列顯示目標 |
| 穩健 | 多重編碼偵測（UTF-8 / BOM / cp950 / Big5 / GBK）、檔案鎖定重試、友善錯誤頁 |

外部連結一律交給**系統預設瀏覽器**開啟，閱讀區內不會載入任何網頁。

## 快速鍵

| `Ctrl + ,` | 開啟／關閉設定面板 |

| `Alt + 左方向鍵` | 回到上一篇文件 |

## 設定面板

按 `Ctrl+,` 或標題列的齒輪鈕開啟。面板會**覆蓋標題列以下的整個視窗**，是一頁
完整的設定畫面，因此每個項目都配有名稱與說明文字。標題列保持可見——無邊框視窗
需要它才能拖曳與關閉，齒輪鈕本身也是收起面板的方式之一（`Esc` 或右上角的
關閉鈕也可以）。視窗不夠高時面板會垂直捲動。

| 區塊 | 項目 | 選項 |
|------|------|------|
| 外觀 | 語言 | 繁體中文 / English / 跟隨系統（預設） |
| | 主題 | 淺色 / 深色 / 跟隨系統（預設） |
| | 字級 | 7～30 pt，與 `Ctrl` `+` / `-` / `0` 連動 |
| | 行高 | 緊湊 142% / 標準 160% / 寬鬆 188% |
| | 內文寬度 | 窄 720px / 中 900px / 不限 |
| 行為 | 檔案監看 | 存檔後自動重新渲染並保留閱讀位置 |
| | 視窗 | 釘選最上層，等同 `Ctrl+P` |
| | 狀態列 | 顯示底部檔案資訊，等同 `Ctrl+/` |
| | 外部連結 | 開啟前先跳出確認 |
| | 還原上次分頁 | 關閉時記住開著的分頁，下次啟動時還原（預設關閉） |
| 重設 | 恢復預設值 | 全部歸零，主題也回到「跟隨系統」 |

分段選擇與開關共用同一種「晶片」外觀：未選取是描邊、選取是強調色實心。

### 語言

介面語言在設定面板「外觀」區的第一列——看不懂目前介面的人，會從第一區的第一列
開始找。切換後**所有開著的視窗立刻更新**（透過 `WindowManager.broadcast_language`），
不需要重開程式。預設「跟隨系統」，取的是 Windows 的**顯示語言**
（`QLocale.uiLanguages()`）而不是地區格式——顯示語言設英文、地區設台灣的機器上，
`QLocale.name()` 會回報 `zh_TW`，那不是我們要問的問題。

字串放在 `languages/zh_TW.json` 與 `languages/en.json`，程式端一律透過
`language.t("鍵")` 取用。用 JSON 查表而不是 Qt 的 `.ts`/`.qm` 工具鏈：全部只有
一百多條字串，純文字檔看得懂 diff、改完存檔就生效，不必多養一道 `lrelease`
編譯步驟。鍵是**扁平的**（分類靠 `titleBar.` / `settings.` 這類前綴），兩份檔案
因此可以用一句 `sorted(a) == sorted(b)` 驗證對齊——回歸測試裡的「語言檔完整性」
就是這樣寫的。

**一句話一個鍵，絕不在程式碼裡拼接。** 中英語序不同（「切換到{target}主題」/
"Switch to {target} theme"），拼接出來的英文語序永遠會是錯的；全形標點
（`（）～／：·`）也一律由翻譯字串整條承載，英文用半形，那是翻譯的一部分。

實作上有四個地方值得記下來：

1. **面板上三分之二的字原本改不了。** `_add_section` / `_add_row` 建的 `QLabel`
   是區域變數，建完就丟；`IconButton` 的 tooltip 也只在建構時設一次。改成建的
   時候把「元件 → 翻譯鍵」登記起來，語言一換走訪登記表就地重設，不重建面板
   （重建會讓捲動位置歸零、晶片的勾選狀態要重同步）。
2. **有三處拿翻譯過的文案當程式邏輯用**，一翻譯就壞，都已改掉：歡迎頁判定原本
   比對產品名稱字串、忙碌提示的還原原本比對訊息前綴（改用 `_status_is_busy`
   旗標）、分頁的 `matches()` 原本比對 tooltip（改比對路徑這個穩定身分——
   翻譯讓它誤判成結構改變就會在拖曳中重建按鈕，那正是 `tab_bar.py` 開頭警告的
   崩潰類別）。
3. **Windows 會自動補標題後綴。** Qt 若發現 `windowTitle` 沒有以
   `applicationDisplayName` 結尾，就自作主張補一段 ` - <displayName>`。
   `main.py` 與 `viewer._update_titles` 的來源一旦分家，工作列會出現
   「note.md — Markdown Reader **- Markdown 閱讀器**」。兩邊同源於
   `t("app.displayName")`，回歸測試用精確標題比對把它釘住。
4. **Qt 內建元件的文字也一併處理了。** 這個專案原本從未載入 `QTranslator`，
   所以右鍵選單與訊息框按鈕一直顯示英文源字串（中文介面配英文右鍵選單）。
   現在切到中文時會載入 Qt 自己的 `qtbase_zh_TW.qm`（本來就隨 PyQt6 打包進去，
   不需要多帶任何東西）。

> **已知限制：** `QFileDialog` 在 Windows 走的是原生對話框，「開啟／取消」這些
> 按鈕的文字**永遠跟隨系統語言**，本程式控制不到。我們能控制的只有對話框標題
> 與檔案類型篩選。要一致就得改用 Qt 自繪版（`DontUseNativeDialog`），但那會
> 失去快速存取與最近使用清單，不划算。

### 系統主題

主題模式預設是 **跟隨系統**：

- 首次啟動時讀取 Windows 的「選擇您的預設應用程式模式」，直接套用對應配色。
- 之後在 Windows 切換深淺色，視窗會**即時**跟著變，不需要重開程式。
- 在設定面板選了「淺色」或「深色」就會鎖定，不再跟隨；想恢復自動就選回「跟隨系統」。
- 標題列的主題切換鈕等同於「切到另一個配色並鎖定」。

偵測優先使用 Qt 6.5+ 的 `QStyleHints.colorScheme()`（即時同步就是靠它的
`colorSchemeChanged` 訊號）；若回報 `Unknown`，才退回讀登錄檔的
`HKCU\...\Themes\Personalize\AppsUseLightTheme`。

### 內文寬度是怎麼實作的

`QTextDocument` 不支援 `max-width`，而 `setDocumentMargin()` 只能四邊一起設定
（上下也會跟著變超大）。因此改用 root frame 的 `frameFormat`，它可以分別指定
四個邊距——把左右邊距設成 `(可視寬度 - 目標寬度) / 2`，就得到一欄固定寬度且
置中的閱讀區。視窗縮放時會即時重算。

**算出同一個邊距就不會去碰 `frameFormat`。** `setFrameFormat()` 會讓整份文件
重新排版，而拖曳視窗邊緣時每一幀都會算一次邊距。實際上大多數時候算出來的是
同一個數字：只改高度時一定相同；選「不限」寬度時左右邊距恆等於預設邊距，
連改寬度都不會變。因此把已套用的值記在分頁上，相同就直接跳過——實測拖曳
30 個 resize 事件，只改高度時重排次數 30 → 0，不限寬時改寬度同樣 30 → 0；
限寬下改寬度的重排是邊距真的變了，必要而保留。文件一重建（`setHtml`）
邊距會回到預設值，那時要讓這個記錄失效，否則會誤判成「沒變」而套不上去。

### 區塊改寫從 O(n²) 降到 O(n)

`qt_html.py` 把 `blockquote` / `pre` / `hr` / `h1` / `h2` 換成 Qt 認得的單格表格。
原本的寫法是走到一個就 `list(parent).index(e)` 找位置、`remove` 再 `insert`——
這三個操作每一個都要掃過父節點的整份子清單，而 Markdown 的區塊多半都是 root
的直接子節點。標題很多的文件（每個 `h1`/`h2` 都要換）就退化成 O(n²)：

| 區塊數 | 改寫前 | 改寫後 | 倍率 |
|---|---|---|---|
| 500 | 4.8 ms | 0.52 ms | 9x |
| 2000 | 77.3 ms | 1.99 ms | 39x |
| 8000 | **2237.5 ms** | **13.8 ms** | **162x** |

倍增比從 4.0x（二次）降到 2.0x（線性）。改法是先蒐集「哪個節點要換成哪個表格」，
再對每個父節點走一次子清單、用 `parent[index] = table` 就地替換——不必
`remove`/`insert` 搬動後面的元素，也省下原本的四趟遍歷。輸出以 15 種文件輪廓
（含巢狀引言、清單裡的引言、連續 `hr`、隨機混合 600 塊）驗證與改寫前逐位元組相同。

### 大文件的渲染：分段先見首屏

一次 `setHtml` 會把整份文件排完版才回來，那段時間介面完全凍結。改成先把
**首屏**（前 40 個頂層元素）交出去，其餘每 400 個元素一塊、在事件迴圈的空檔
補上。實測（`tools/benchmark_render.py` 的合成文件，實際在閱讀器視窗量）：

| 文件 | 關閉分段·首屏 | 分段·首屏 | 分段合計 |
|---|---|---|---|
| 標題密集（144 KB） | 1470 ms | **394 ms** | 919 ms |
| 混合（28 KB） | 252 ms | 162 ms | 285 ms |
| 長篇散文（174 KB） | 342 ms | 272 ms | 384 ms |

首屏的下限是 Markdown → HTML 的轉換時間（那一段沒辦法分段），標題密集的
文件光轉換就要 356 ms，所以 394 ms 裡真正屬於 Qt 排版的只剩幾十毫秒。

**反直覺的地方：切得越細，連總時間都變短。** 一開始想的是「首屏 + 剩下一整塊」，
實測反而比不分段還糟——單次 `insertHtml` 塞一大段進已經有內容的文件特別貴：

| 剩下切成幾塊 | 總計 | vs 一次到底 | 最久一塊 |
|---|---|---|---|
| 1 | 1915 ms | 2.17x | 1915 ms |
| **16** | **952 ms** | **1.08x** | **83 ms** |
| 64 | 985 ms | 1.12x | 32 ms |

所以用「每塊固定 400 個元素」而不是「固定切成 N 塊」——每塊的凍結時間才有
上界，不會隨文件變大而惡化。（試過 `beginEditBlock` 與關閉 undo，都沒有幫助。）

兩個實作上的坑：

1. **接合處要不要先開一個新區塊，要看片段的第一個元素是什麼。**
   `insertHtml` 會把片段的第一個區塊併進游標所在的區塊，片段以 `<p>`、`<h3>`、
   清單開頭時就會和前一段黏成一段（實測整份少掉一個換行）；而表格在 Qt 裡
   自成一個 frame，不會併——這時多開一個區塊反而留下一個空段落。九種文件輪廓
   逐一實測，只有條件式的版本每一種都與一次到底逐字元相同。
2. **任何需要「完整文件」的操作都得先補完。** 搜尋、跳錨點、切分頁、捲動位置
   還原都是。切分頁尤其有兩條路徑——分頁列切換走 `activate_tab`，開新檔案走
   `_add_tab`——兩條都要補，少了任一條，被切走的分頁就永遠停在只有首屏。

### 圖片載入失敗時

圖片載不到時**不會**留下 Qt 內建的那張 16×16 灰色小檔案圖
（`:/qt-project.org/styles/commonstyle/images/file-16.png`），而是自己畫一個虛線框：
左邊 `assets/icons/image_broken.svg`，右邊上行是 **alt 文字**、下行是**你在 Markdown
裡寫的那個路徑**。

Qt 的預設有兩個真正的問題，換掉之後一起解決：

1. **不顯示 alt text。** `QTextDocument` 根本不畫替代文字，所以
   `![重要的架構圖](x.png)` 壞掉時，你完全看不出那裡本來是什麼。
2. **不告訴你哪個路徑壞了。** 一份文件裡十張圖壞三張，你得自己一張張對。

攔截點是 `browser.MarkdownBrowser.loadResource()`——它本來就被覆寫了（任務清單的
核取方塊、過寬圖片的縮放都在那裡）。載入失敗時原本會回傳 null，Qt 才去用它的預設值；
改成回傳自己畫的圖，Qt 就沒機會插手。

**一個不明顯的坑：Qt 會把 alt 丟掉。** `alt` 屬性在產生的 HTML 裡是有的，但 Qt 解析
之後完全不留（`charFormat` 與 `toolTip` 都是空的），而 `loadResource` 只拿得到 url。
所以 alt 必須在交給 Qt 之前先自己抽出來（`document.image_alts()`）、在 `setHtml`
之前交給閱讀區（`browser.set_image_alts()`）。

**而且那份對照表的鍵不能用原始 src。** `loadResource` 收到的是 Qt 用 baseUrl 解析過的
絕對 url——`docs/a.png` 會變成 `file:///.../docs/a.png`，拿原始 src 當鍵一定查不到、
alt 就會靜靜地失效。所以 `set_image_alts()` 會先用同一個 baseUrl 把每個鍵解析一次。
回歸測試裡有一條專門守這件事，並且會先斷言「解析後的 url 和原始 src 確實不同」，
免得哪天環境變了讓那條測試變成恆真。

圖示本身遵守既有的圖示規範：`16×16` viewBox、純描邊、`{color}` 佔位符隨主題著色。
它是這套圖示裡第一個帶封閉方框的形狀（其餘 18 個都是開放形狀），這是「圖片」這個
概念避不掉的；好在它只出現在內文裡，旁邊沒有其他圖示可比。

### 搜尋在大文件上的兩個成本

`Ctrl+F` 會高亮**所有**符合項，目前所在那一項用另一種顏色。長文件上這件事有
兩個成本，各自的處置寫在 `app/find_bar.py` 的模組說明裡：

| 成本 | 處置 |
|------|------|
| 比對要掃過整份文件，每按一個鍵就掃一次會打到卡字 | **輸入防抖**：停手 120 ms 之後才真的掃。清空搜尋詞沒有掃描成本，不進防抖、立刻生效 |
| 高亮是把 N 個 `ExtraSelection` 交給 Qt | 按「下一個」時其實**只有兩筆換色**，因此整份 selection 留著重用、只換那兩筆 |
| 符合項極多時，光是交出去就很重 | **高亮上限** 2000 筆。比對數量不受限（狀態列的 `N / M` 仍是實數），只有畫出來這件事有上限 |

`Enter` 會先把還在等的那次防抖兌現，不會拿上一個鍵打完時的舊結果來跳，
結果與沒有防抖時完全一致。

超過高亮上限時，取以目前這一筆為中心的一段窗格，使用者所在的位置附近一定
畫得到；而且只有在目前這筆跑出窗格外時才重新置中——每跳一筆就滑動窗格的話，
「只換兩筆」那條快路徑會永遠用不到。此時狀態列會標明只高亮鄰近筆數，
免得捲到遠處看見沒上色的相符字以為是壞了。

有一個地雷值得記下來：`setHtml` 是把**同一個** `QTextDocument` 清空再填回，
先前建好的 `QTextCursor` 會整批被折到位置 0。換主題、換字級都會觸發重新渲染，
所以渲染完必須叫搜尋列重算，否則高亮會整片塌在文件開頭
（回歸測試裡那條的失敗簽名就是三筆位置全部相同）。

### 搜尋的比對選項

搜尋框右側兩顆可切換的按鈕，亮起（強調色）代表開啟，狀態會留到下次啟動：

| 按鈕 | 快速鍵 | 對應的 Qt 旗標 |
|------|--------|----------------|
| `Aa` 區分大小寫 | `Alt + C` | `FindCaseSensitively` |
| `[a]` 全字拼寫相符 | `Alt + W` | `FindWholeWords` |

比對本身完全交給 `QTextDocument.find()` 的旗標，這邊一行比對邏輯都沒有自己寫。
兩顆按鈕的快速鍵用 `QShortcut` 而不是輸入框的事件過濾器——tooltip 上就標著
`Alt+C`，只在輸入框有焦點時才作用的話，對「剛用滑鼠捲過文件」的人那行提示
就是騙人的。

**全字對中文的實際效果要有心理準備。** Qt 的全字是以詞邊界判定，而中文不用
空白斷詞，所以一整串沒有空白的中文會被當成同一個詞：在「全文搜尋」裡找
「搜尋」，開了全字之後**不算相符**（實測），只有整串剛好等於搜尋詞才算。
這是 `FindWholeWords` 一貫的語意、和其他編輯器一致，因此不做中文特例；
回歸測試裡有一條專門把這個行為釘住，免得日後被當成 bug 而加上特例。
順帶一提，底線在 Qt 眼中是詞的分隔符：`my_var` 用全字找 `var` 會相符。

實作上有兩個小地雷：

1. **`blockSignals` 會連圖示著色一起擋掉。** 「依設定把按鈕勾起來」不能反向
   送出訊號（否則 viewer 會把剛讀到的值再寫回去一次），但 `IconButton` 的
   重新著色正是掛在 `toggled` 上的，只 `setChecked` 會勾起來卻停在灰色。
   所以 `set_checked_silently()` 自己補一次 `refresh_icon()`。
2. **測試不能掃 `_buttons` 那份清單。** 漏加進清單的按鈕不在清單裡，掃清單
   反而永遠掃不到（實測把兩顆選項鈕拿掉，掃清單的版本照樣全綠）。語言測試
   改掃搜尋列**實際的子元件**的 tooltip——這和設定面板那條是同一個理由。

選項存進 QSettings，但**刻意不廣播到其他視窗**：其餘視窗可能正開著自己的
搜尋，被外部改掉比對規則會讓畫面上的高亮無故變動。存下來的值只影響下一個
開啟的視窗。

### 基準工具

`tools/benchmark_startup.py` 顧啟動、`tools/benchmark_render.py` 顧渲染。
渲染基準分兩層量：Markdown → HTML（純 Python）與 `setHtml` 的解析與版面計算，
各自對四種文件輪廓（標題密集／長篇散文／程式碼密集／表格密集）加一份混合文件
獨立比對——渲染成本不是只跟位元組數走，只量一份「大檔」看不到結構相關的退步。

```bash
py -3.13 tools/benchmark_render.py
```

判定以**最小值**為準（干擾只會讓時間變長，不會讓程式跑得比實際更快），
容忍 15%，超出就以結束碼 1 收場。要讓數字穩到撐得起這個門檻踩了三個坑，
都寫在模組說明裡：每個指標各開一個新行程（同行程連續量，後量的會整批快 40%）、
Qt 端用獨立的 `QTextDocument` 不開視窗（視窗的合成雜訊讓同一份文件量到
272 / 493 / 490 / 349 ms）、丟掉兩次暖機並在每次取樣前 `gc.collect()`。
現在八項指標跨三輪的擺盪都在 ±3% 以內。

這套判定驗證過確實抓得到問題：把 `qt_html` 換回修好之前的 O(n²) 版本，
`md_headings` 由 373 ms 變成 562 ms（+51%）被標為退步、結束碼 1，
其餘七項全部持平——同時告訴你「哪一類文件變慢」以及「慢在哪一層」。

## 分頁與單一實例

### 什麼情況會開新分頁

| 動作 | 結果 |
|------|------|
| 在檔案總管雙擊 `.md` | 送給既有視窗開成新分頁；沒有視窗在跑時才開新程式 |
| 點文件裡的本機 `.md` 連結 | 開成新分頁（原本那篇留在原分頁，隨時切得回去） |
| `Ctrl + O` 選檔、拖放檔案 | 開成新分頁 |
| `Ctrl + T` 或分頁列的「＋」 | 開一個空白分頁 |

同一個檔案不會重複開：已經開著時直接切過去，不會多出一個一樣的分頁。

分頁列**永遠顯示**（含單一分頁）——隱藏的話單開一個 .md 就沒有分頁可以抓，
永遠拖不去別的視窗合併。分頁太多時可以在分頁列上橫向捲動，中鍵點分頁也能關閉。

### 分頁拖曳（比照瀏覽器）

| 手勢 | 結果 |
|------|------|
| 在分頁列內左右拖 | 即時重排，跨過鄰居的中心點就交換位置 |
| 拖出分頁列（任一方向約 48px）再放開 | **拆分**：該分頁變成一個新視窗，出現在放開的位置 |
| 拖到**另一個視窗**的分頁列上放開 | **合併**：插進游標所指的位置，並切換到該分頁 |

拖出分頁列後會有一個**半透明的分頁縮影**跟著游標，**按下時抓的那一點會一直
待在游標底下**（比照瀏覽器）——抓分頁左緣就從左緣拖著走，抓右緣就從右緣。
縮影下方的徽章即時預告放開會發生什麼：**合併**（強調色實心）、
**拆分為新視窗**（描邊）、**無動作**（灰）。要合併時，目標視窗的分頁列上還會
出現一條**強調色細線**，標出分頁會插進哪個縫隙；此時縮影會**變得更透明**
（0.9 → 0.45）——相對跟隨讓縮影蓋在游標正下方，而那正是指示線所在的位置，
不讓路的話抓分頁中央拖去合併時指示線會被完全遮住。預告、指示線與放開時的實際
決策走同一段程式（同一個 `drop_target_at` 結果），不會說一套做一套。
放開點的判定規則：

- 放開在**本列上** → 純重排。
- 放開在**容忍帶內（超出列不到 48px）** → 只允許合併：游標下有別的視窗的
  分頁列就合併，沒有就不動作——手滑超出幾個像素不會噴出一個新視窗。
  這條也讓「兩個視窗相鄰、分頁列同高」時橫向拖過去能直接合併。
- 放開在**容忍帶外** → 有目標就合併，沒有就拆分成新視窗。

細節與取捨：

- 所有視窗都在**同一個行程**裡（瀏覽器模型）。拆分／合併是把分頁物件直接
  搬過去——已渲染的內容、返回歷史、捲動位置都原封不動，不會重新讀檔。
- 合併時目標視窗的主題可能不同，搬過去的分頁會用目標視窗的主題重新渲染，
  不會出現「深色視窗裡有一頁是淺色」。
- 空掉的來源視窗自動關閉；最後一個視窗關閉時程式結束。
- 單一分頁拖到空白處不做事（那等於拖整個視窗，標題列本來就能做）。
- 雙擊 `.md` 轉交進來的檔案，開在**最後作用中**的那個視窗。
- 「還原上次分頁」目前只記住**最後關閉**的那個視窗的分頁（多視窗的完整
  還原是已知限制，見下方）。

實作上最容易踩的三個坑寫在 `app/tab_bar.py` 的模組與類別註解：

1. 按下分頁會觸發 activate → set_tabs，若在拖曳中重建按鈕，被按住的那顆會
   被銷毀、滑鼠抓取跟著消失。set_tabs 因此在結構沒變時只就地更新樣式。
2. 撕下狀態不能只靠移動事件設定，**放開時要用放開點重新判定**。兩個視窗
   相鄰（間距小於容忍帶）時，游標已經在對方分頁列上、卻還沒離開本列的
   容忍帶——只信移動事件設的狀態，放開就什麼都不做。
3. 縮影相對跟隨的代價是**它必然蓋住游標**，而合併目標原本是用
   `QApplication.topLevelAt` 決定的。Qt 在 Windows 走
   `ChildWindowFromPointEx(..., CWP_SKIPINVISIBLE)`，只跳過隱藏的視窗、
   不跳過 `WS_EX_TRANSPARENT`，所以它會回傳縮影。實測 60 個落在縮影內的
   點，`topLevelAt` 100% 抓到縮影。

#### 為什麼合併的命中測試改用原生 `WindowFromPoint`

`topLevelAt` 抓到縮影**不會**讓分頁併到縮影上——縮影既不是來源視窗也不在
候選清單裡，`drop_target_at` 的堆疊判定會整段失效，**安靜地退回「最後作用
優先」的幾何掃描**。後果是分頁併進一個被完全遮住、使用者根本看不到的視窗，
而且因為幾何掃描有時剛好猜對，症狀是時好時壞。

`win32.top_level_hwnd_at()` 改用 `WindowFromPoint` + `GetAncestor(GA_ROOT)`：
它是唯一會跳過 `WS_EX_TRANSPARENT` 的原生點查詢。實測同樣 60 個點，
0% 抓到縮影、100% 答出底下的視窗。成本比其他可行方案低兩個數量級
（`QApplication.widgetAt` 挖 1×1 洞在 dpr 1.5 下只有一半準確率；
`hide()`/`show()` 或 `setMask` 打洞各要 2.3–2.4 ms，跑在每個滑鼠移動事件上
是 125 Hz 預算的三成）。

這也讓 `Qt.WindowType.WindowTransparentForInput` 從「視覺選擇」升級為
**功能相依**：它是那個 `WS_EX_TRANSPARENT` 的唯一來源，只留
`WA_TransparentForMouseEvents` 產生不出這個 exstyle，拿掉之後連
`WindowFromPoint` 也會抓到縮影。

邏輯座標要換成原生像素才能問 `WindowFromPoint`。不能全域乘一個
`devicePixelRatio`：Qt 的高 DPI 換算是「每個螢幕各自縮放、原點守恆」，
多螢幕不同縮放時只有取點所在那個螢幕的原點與比例才會對。換算完還會回頭
檢查解出來的視窗是否真的含這個點——若在某種多螢幕組合下失準，就退回既有的
幾何掃描，寧可退化成修正前的行為，也不拿一個錯的視窗當答案。

### 單一實例是怎麼做的

第二個行程啟動後，會先透過 Windows 具名管道（`QLocalSocket`）試著連上既有實例：

- **連得上** → 把路徑送過去、把對方的視窗叫到前景，然後自己結束，不開視窗。
- **連不上** → 自己就是第一個實例，改當監聽端。

這個探測不會拖慢正常啟動：沒有實例在跑時具名管道會**立刻**回報失敗（實測
0.1～0.5 ms），不會等到逾時。

轉交本身的成本也很低，實測（扣掉量測工具本身的開銷）：

| 打包方式 | 雙擊第二個檔案到分頁出現 |
|---|---|
| 資料夾版 | **約 171 ms** |
| 單一 exe | 約 1,064 ms |

單一 exe 慢的原因和冷啟動一樣——即使只是要送一個路徑然後結束，也得先把整包
解壓到 `%TEMP%`。**常用檔案關聯的話，資料夾版的差距在這裡比冷啟動更有感。**

實作上有兩個容易踩到的點，都寫在 `app/single_instance.py` 的註解裡：

1. **不要用 `waitForBytesWritten()`**。Windows 的 `QLocalSocket` 上 `flush()` 不
   保證清空待寫緩衝區，而 `bytesWritten` 訊號在這種小量寫入後不會可靠地再發一
   次，於是它會一路空等到逾時——單這一項就讓每次雙擊多花整整一秒。改成交給
   `disconnectFromServer()`：它會先送完待寫資料再關閉。
2. **收方要能處理「資料還沒進緩衝區就已斷線」**。送方寫完立刻要求關閉，
   `readyRead` 與 `disconnected` 誰先到並不固定。少了補讀那一步會讀到空字串，
   症狀是「分頁開出來卻是空白」。

> 量測時注意：把送方和收方寫在同一個行程裡會失真——送方的 `waitFor*` 會鎖住事
> 件迴圈，收方根本沒機會處理連線。要用兩個真正的行程量。

### 原生轉交器（MarkdownOpen.exe）

上面的轉交成本還能再砍。轉交那 170 ms／1064 ms 幾乎全花在「載入 python313.dll
與整套 PyQt6」——即使那個行程只是要把路徑送出去就結束。`src_cpp/md_open/` 是
一支 38 KB 的原生 Win32 程式，只做三件事：

1. 試著連上具名管道（Qt 的 `QLocalServer` 在 Windows 上就是 `\\.\pipe\<名稱>`
   的位元組模式管道，用 `CreateFile` + `WriteFile` 就能當它的客戶端，不需要 Qt）。
2. 連得上就把路徑送過去、結束；連不上就啟動本體，參數原封不動傳過去。
3. 用具名互斥鎖排隊：一次選取多個 `.md` 按 Enter 時，第一個負責帶起本體，
   其餘等管道出現後轉交，不會各自開一個視窗。

實測（`tools/benchmark_handoff.py`，各 10 次取最小值，量測工具本身的
地板 9 ms 已列出供對照）：

| 動作 | 直接啟動本體 | 經原生轉交器 |
|---|---|---|
| 已開著時再雙擊（資料夾版） | 169 ms | **10 ms** |
| 已開著時再雙擊（單一 exe） | 1,046 ms | **9 ms** |
| 冷啟動到視窗出現（資料夾版） | 622 ms | 634 ms（+22～26 ms） |

冷啟動多出的 22～26 ms 是多開一個行程的固定成本；轉交器會在本體的管道
開起來後（早於視窗出現）就退場，不會殘留。

把檔案關聯指向轉交器就能吃到這個加速（`build.ps1` 完成訊息也會提示這個路徑）：

```bash
py -3.13 tools/install_association.py --target "D:\software\Customize-Open-File\md\dist\MarkdownReader-onedir\MarkdownOpen.exe"
```

轉交器由 `build.ps1` 的第 5 步自動編譯（需要 MSYS2 UCRT64 的 g++；沒有就
略過，主程式不受影響）。要在 VS Code／Cursor 裡改它：`.vscode/` 已設好
IntelliSense（對準 UCRT64 g++）、`Ctrl+Shift+B` 建置（旗標與 build.ps1 一致），
以及 `F5` 用 gdb 除錯（會另編一份帶符號、未 strip 的 `MarkdownOpen-debug.exe`
——發佈版的 `-s` 會把符號拔光，直接除錯發佈版什麼都看不到）。圖示是內嵌的必要品：關聯腳本拿「目標 exe 的第 0 個
圖示」當 `.md` 的檔案圖示，沒有它所有 `.md` 都會變白紙。

幾個實作上的防呆，都寫在 `main.cpp` 的註解裡：

- **等待以本體行程的狀態為界，不是死板的時鐘。** 本體啟動就當機 -> 立刻放棄
  （實測 138 ms）；本體 GUI 起來了卻始終沒開管道（`listen()` 失敗）-> 寬限
  4 秒後放棄（實測 5.1 s），不會握著排隊鎖空等滿 15 秒。
- **管道名稱兩邊寫死，靠測試鎖住一致性**：`tools/smoke_test.py` 會比對
  `main.cpp` 的 `kPipePath` 與 `config.IPC_SERVER_NAME`，改到不同步立刻紅燈
  ——否則不會有任何錯誤訊息，只是安靜退化成每個檔案開一個視窗。
- **送出前呼叫 `AllowSetForegroundWindow`**：前景權限在剛被雙擊的行程手上，
  不轉讓的話既有視窗只能在工作列閃爍。
- **管道「存在但忙」要重試，不能一次放棄**：這個狀態代表本體一定活著（管道會
  隨行程消失），只是還沒回到事件迴圈。放棄的代價是誤判「沒有實例」再生一個
  完整的本體行程（600 ms 起跳），所以忙碌重試的上限放到 3 秒。
- **收方不能在 socket 的訊號裡直接做重活**（這是 Python 端 `single_instance.py`
  的相對修正）：`readyRead` 來自 Qt 管道讀取回呼，在那個框架裡直接
  「拆 socket → 開分頁 → 渲染大檔」，會與其他排隊連線的管道回呼交錯，實測
  三條連線背靠背時必定以 `0xC0000005` 崩潰在原生層。`deliver()` 改用
  `QTimer.singleShot(0, ...)` 把派送推回事件迴圈。`tools/smoke_test.py` 有
  對應的回歸測試（掛起本體 + 三連發）。

### 大檔的載入回饋

1 MB／5000 行的 Markdown，轉換加排版約需 700 ms，期間介面完全凍結。
超過 `config.BUSY_FEEDBACK_BYTES`（256 KB）的檔案會在**凍結開始之前**
顯示等待游標與「正在載入 <檔名>…」，讓使用者知道程式在動而不是當掉。

兩個實作上的要點：

- 提示必須用 `repaint()` 立刻重繪，不能用 `processEvents()`。後者會重入
  事件迴圈，在載入途中處理其他訊號——本專案已經為這種重入付過代價
  （見 `app/single_instance.py` 關於管道回呼的註解）。
- 還原游標一定要放在 `finally`：讀檔失敗等例外路徑若沒還原，等待游標會
  永遠卡在畫面上。而且必須成對還原、不能清空整個堆疊，因為邊緣縮放
  （`FramelessResizer`）也在用覆蓋游標。

門檻設在 256 KB 而不是更小：小檔渲染在百毫秒內完成，閃一下游標反而是雜訊。

### 渲染快取

字級縮放與主題切換原本都要整份重跑 Markdown 轉換，大檔按一次 Ctrl+= 就要等
七百毫秒。實際上這兩件事只影響外層樣式，**HTML 本體沒有變**。

`DocumentTab` 因此以「主題」為鍵快取轉換結果，值是 `(原始文字, HTML)`：

```python
cached = self._html_cache.get(theme)
if cached is not None and cached[0] is self.text:
    return cached[1]
```

比對用 `is` 而不是 `==`：重新載入檔案會把 `self.text` 換成新的字串物件，
快取自然失效，不需要在每個改動內容的地方記得手動清快取——那種「忘了清」
的錯誤會表現成「檔案改了但畫面沒更新」，比慢還糟。兩個主題各留一份，
來回切換都是命中。

同時 `document.markdown_to_html()` 改為重用 `markdown.Markdown` 實例。
**重用一定要先 `reset()`**：該物件會累積註腳、參考連結、toc 與 htmlStash
（本專案用來把 fenced code 抽出再包成表格的暫存區）。少了 reset，第二份
文件會帶著第一份的註腳，程式碼區塊的編號還會整段錯位。

實測（1 MB／5272 行的 CHANGELOG.md）：

| 操作 | 改動前 | 改動後 |
|---|---|---|
| 字級縮放 | 713 ms | **176 ms**（−75%） |
| 主題切換（來回） | 713 ms | **180 ms**（−75%） |
| 首次開啟 | 600 ms | 601 ms |
| 連續轉換不同文件 | 518 ms | 524 ms |

誠實的結論：**省下來的全部來自 HTML 快取**。重用轉換器聽起來像優化，但
建構一個 `markdown.Markdown` 只要 0.10 ms——小檔省 36%（0.14 ms）、中檔
省 11%、大檔只省 0.4%，在量測誤差裡。留著它是因為沒有成本，不是因為有效。

首次開啟沒有變快，因為那一次本來就是 cache miss，該做的轉換一次都少不了。
要再快就得動 Markdown 轉換本身或 Qt 的排版，那是另一個層級的改動。

回歸測試在 `tools/smoke_test.py` 的「渲染快取」區塊（18 項），比對的是
「重用的輸出與全新轉換器逐字元相同」，而不是「看起來沒壞」。

### 還原上次的分頁

設定面板的「還原上次分頁」**預設關閉**。開啟後，關閉視窗時會記下當時開著的檔案
與作用中的分頁，下次啟動時還原。

還原採**延後載入**：只先建立空的分頁並記住路徑，等真的切過去才讀檔與渲染。
否則還原十個分頁就要付十次 Markdown 轉換的代價，啟動會明顯變慢。

## 打包成單一 exe

```bash
py -3.13 -m PyInstaller --noconfirm --clean build.spec
```

```bash
powershell -ExecutionPolicy Bypass -File build.ps1
```

`build.ps1` 也支援 `-OneDir`（資料夾版）與 `-Clean`（先清除舊產物）。

### 純 CLI 形式（不使用 spec）

```bash
py -3.13 -m PyInstaller --noconfirm --clean --onefile --windowed --noupx --name MarkdownReader --icon assets/app.ico --add-data "assets;assets" --hidden-import PyQt6.QtSvg --exclude-module PIL --exclude-module numpy --exclude-module pyqtgraph --exclude-module PyQt6.QtWebEngineCore --exclude-module PyQt6.QtWebEngineWidgets --exclude-module PyQt6.QtQml --exclude-module PyQt6.QtQuick --exclude-module PyQt6.QtMultimedia --exclude-module PyQt6.QtSql --exclude-module PyQt6.QtTest --exclude-module tkinter main.py
```

> **兩個要注意的地方**
> 1. 這種形式會自動產生一份 `MarkdownReader.spec`，**會覆蓋同名檔案**。專案裡的設定檔因此取名 `build.spec`，才不會被蓋掉。
> 2. `--exclude-module PIL --exclude-module numpy` 一定要加。`pygments.formatters.img` 會 import PIL，PIL 的 hook 又把 numpy 拉進來，光這兩個就會讓 exe 從 30 MB 膨脹到 60 MB（含 20 MB 的 OpenBLAS 與 7.8 MB 的 AVIF 外掛）。本程式只用 `HtmlFormatter` 產生 HTML，不需要它們。
>
> CLI 形式無法過濾 DLL，所以仍會包進 `opengl32sw.dll`（20 MB）等用不到的二進位；`build.spec` 有做這層過濾，這也是兩者差距的來源。

### 各參數的用意

- `--windowed`（等同 `--noconsole`）：**隱藏終端機視窗**，這是最關鍵的一個。
- `--add-data "assets;assets"`：所有圖示都是外部 SVG 檔，一定要打包進去（Windows 用 `;` 當分隔符）。程式端一律透過 `app/resources.py` 的 `resource_path()` 讀取，會自動處理 PyInstaller 的 `sys._MEIPASS`。
- `--hidden-import PyQt6.QtSvg`：搭配 `main.py` 頂端的顯式 `import PyQt6.QtSvg`，確保 Qt 的 SVG 插件（`qsvg.dll` / `qsvgicon.dll`）一併被收錄。**漏掉的典型症狀是「原始碼跑起來圖示正常、打包後全部變空白」。**
- `--noupx`：UPX 壓縮 Qt 的 DLL 經常導致程式無法啟動。
- `--exclude-module ...`：排除用不到的 Qt 模組與 PIL / numpy。
- `build.spec` 另外過濾了幾個大型 DLL：`opengl32sw.dll`（20 MB，Mesa 軟體 OpenGL 後備，純 widget 程式走 raster 繪製用不到）、`Qt6Pdf.dll`、`libcrypto-3.dll` / `libssl-3.dll`（QtNetwork 的 TLS 後端，本程式不連網）。若日後在極舊的顯卡或虛擬機出現空白視窗，把 `build.spec` 裡 `EXCLUDE_BINARIES` 的 `opengl32sw.dll` 拿掉重新打包即可。

打包尺寸實測：

| 打包方式 | 大小 |
|---|---|
| 未排除 PIL / numpy 的 CLI 形式 | 60.4 MB |
| `build.spec`（含 DLL 過濾） | **29.8 MB** |

### onefile 還是 onedir？

**如果要設成 `.md` 的預設開啟程式，強烈建議用資料夾版。**實測（各跑 8 次取最小值）：

| 打包方式 | 冷啟動到視窗出現 | 已開著時再雙擊一個檔 | 體積 | 行程數 |
|---|---|---|---|---|
| 單一 exe（`--onefile`） | **1,387 ms** | **1,064 ms** | 31.3 MB（單檔） | 2（啟動器 + 本體） |
| 資料夾版（`--onedir`） | **625 ms** | **171 ms** | 73 MB（資料夾） | 1 |

差距的來源很單純：單一 exe 每次啟動都要把整包約 30 MB 解壓到 `%TEMP%`，資料夾版直接載入現成檔案。

第三欄是加上分頁功能後才有的差距，而且比冷啟動更有感——即使新行程只是要把路徑
送給既有視窗然後立刻結束，單一 exe 一樣得先完整解壓一次。日常會頻繁雙擊 `.md`
的話，這一欄才是真正該看的數字。

> 「兩個行程」不是錯誤：單一 exe 的啟動器會再開一個本體行程，工作管理員因此會
> 看到兩筆同名項目，那是 PyInstaller 的架構，不是程式開了兩份。

建置資料夾版：

```bash
powershell -ExecutionPolicy Bypass -File build.ps1 -OneDir
```

輸出在 `dist\MarkdownReader-onedir\MarkdownReader.exe`。刻意不用預設的 `dist\MarkdownReader\`，是為了避免和單一 exe 的 `dist\MarkdownReader.exe` 只差一個副檔名而相鄰——清理或搬移時很容易誤刪對方。

換成資料夾版之後，記得重新指向檔案關聯：

```bash
py -3.13 tools/install_association.py --target "D:\software\Customize-Open-File\md\dist\MarkdownReader-onedir\MarkdownReader.exe"
```

### 啟動速度是怎麼調的

除了打包方式，程式本身也做過一次量測與調整：

| 項目 | 結果 |
|---|---|
| 匯入模組（PyQt6 + markdown + pygments） | 約 90 ms，沒有優化空間 |
| **啟動時重複渲染** | 已修正，省下約 180 ms |
| 建立主視窗 | 約 470 ms，其中大部分是 Qt 元件子系統的一次性初始化 |
| 延後建立搜尋列／設定面板 | **實測無效**，不採用 |

「重複渲染」是指：`__init__` 先套用主題並渲染一次（此時還沒載入檔案，畫的是歡迎頁），緊接著 `open_path` 又渲染一次真正的文件——第一次完全白做，而首次 Markdown 轉換要花 78 ms。現在啟動時的 `apply_theme` 帶 `render=False`。

至於「延後建立隱藏的元件」，一開始看起來很有搞頭（單獨量搜尋列要 146 ms），但那是誤讀：那只是該行程中第一個被建立的元件，吸收了 Qt 的一次性初始化，換成別的元件也一樣。實測不建立它反而更慢，屬於量測雜訊，因此沒有採用。單次啟動的雜訊約 ±150 ms，比這個量級更小的優化在這個環境量不出來。

```bash
py -3.13 tools/smoke_test.py
```

| 參數 | 用途 |
|---|---|
| `--only 分頁` | 只跑名稱含該字串的區塊 |
| `--list` | 列出所有區塊 |
| `--runs 20` | 提高關閉穩定度測試的重複次數（預設 12） |

關閉穩定度。

### 為什麼有些項目要開子行程

PyQt6 對「虛擬函式（`resizeEvent`、`eventFilter`）裡的未攔截例外」是**致命**的：
不會拋出 Python 例外讓你 try/except，而是直接以 `0xC0000409` 中止行程。這種問題
在同一個行程裡測不到，只能開子行程看結束碼。子行程一律加 `-u`，否則中止時
緩衝區裡的輸出會整段消失，連死在哪一行都看不出來。

### 為什麼單一實例的測試要用專屬管道名稱

Windows 允許同一個管道名稱有多個監聽者。開發時如果剛好有一個真的
MarkdownReader 在跑，測試的送方會連到它去，測試伺服器什麼都收不到，
看起來像功能壞掉。測試因此改用帶行程編號的名稱。

同理，測試「關閉視窗」時如果有殘留實例佔著管道，新行程會轉交後立刻結束，
`WM_CLOSE` 根本沒送到——那會是一整批安靜的假通過。真的踩過，所以測試會在
「視窗還沒出現行程就結束」時直接判失敗。

## 啟動速度基準測試

任何會碰到啟動路徑的改動（新增元件、調整渲染流程、換打包方式）之後跑一次，
確認沒有把啟動變慢：

```bash
py -3.13 tools/benchmark_startup.py
```

通過回傳 0、有項目退步回傳 1，可以直接串進 CI 或 pre-commit。

| 參數 | 用途 |
|------|------|
| `--runs N` | 取樣次數（預設 8，雜訊大時調高） |
| `--target exe\|source\|both` | 只量打包後的 exe、只量原始碼各階段，或兩者 |
| `--tolerance 0.15` | 容忍的變慢比例（預設 15%） |
| `--update-baseline` | 把這次結果存成新的基準線 |
| `--json` | 機器可讀輸出（進度訊息走 stderr，可直接接管線） |

量測分兩層：**打包後的 exe**（從行程啟動到視窗真的出現，使用者實際感受到的時間）
與**原始碼各階段**（匯入、QApplication、主視窗建構、show 到首幀）。exe 變慢時，
靠第二層判斷是程式碼問題還是打包問題。

### 為什麼用最小值而不是平均或中位數

連續啟動的時間本來就會跳動，單次差距可達 ±150ms。關鍵在於這些干擾（背景程式、
磁碟快取、CPU 排程）只會讓時間**變長**，不會讓程式跑得比實際更快，所以最小值
最接近「沒有被干擾時的真實成本」。實測連續三輪的穩定度：

| 統計量 | source_total 三輪結果 | 擺盪 |
|---|---|---|
| 中位數 | 674 / 712 / 686 ms | 約 ±5% |
| **最小值** | **585 / 596 / 596 ms** | **約 ±2%** |

這個差別是有實質後果的：在主視窗建構子注入 120ms 延遲後，用「中位數 + 20% 容忍度」
判定會**漏抓**（只有 +19%），改用「最小值 + 15% 容忍度」則正確標為退步
（`source_ctor` +28%、`source_total` +18%，結束碼 1）。這個注入實驗是這套測試的
驗收條件之一。

### 其他設計

- 第一次啟動當暖機，不列入統計。
- 量測前會把視窗幾何與所有設定固定成已知值（否則上次留下的字級或視窗大小會影響
  版面計算時間），**結束後完整還原使用者原本的設定**。
- 除了和基準線比對，另有絕對上限（例如資料夾版 1800ms）當作沒有基準線時的保底。
- `tools/startup_baseline.json` 記錄的是**某台機器上**的數字，換機器一定不同；
  換機器時先跑一次 `--update-baseline` 重新建立。

## 改完程式之後的重新編譯流程

設定過檔案關聯之後，每次改完程式固定跑這三步：

```bash
taskkill /F /IM MarkdownReader.exe 2>nul
powershell -ExecutionPolicy Bypass -File build.ps1 -OneDir
py -3.13 tools/benchmark_startup.py
```

第二行的打包方式要**對應你的關聯指向哪個版本**（見下方），第三行順便確認這次改動
沒有把啟動拖慢。

`build.ps1` 兩種模式都會自動檢查相依套件、必要時產生圖示，並在結尾印出測試指令與
註冊關聯的指令，不需要自己記參數。

### 為什麼第一步要先關掉程式

程式還開著時 PyInstaller 無法覆寫執行檔，兩種打包方式都會失敗：

```
PermissionError: [WinError 5] 存取被拒。: '...\dist\MarkdownReader.exe'
```

而且是跑到**最後一步才失敗**，前面二十幾秒的分析與打包全部白做。舊的執行檔不會
損壞，只是沒被更新——所以雙擊 `.md` 仍然會開，只是開到改動前的版本。

### 為什麼要指定正確的打包方式

| 關聯指向 | 必須用的指令 |
|---|---|
| `dist\MarkdownReader.exe`（單一 exe） | `build.ps1`（不加參數） |
| `dist\MarkdownReader-onedir\MarkdownReader.exe`（資料夾版） | `build.ps1 -OneDir` |

**用錯的那個編譯，關聯指向的檔案不會被更新，而且完全沒有錯誤訊息。**實際會看到：

```
onefile (剛重新編譯): Aug 25 00:16
onedir  (關聯指向這個): Aug 24 23:04   <- 完全沒動
```

症狀就是「我明明改了程式，雙擊開起來卻還是舊的」。不確定目前指向哪個時：

```bash
reg query "HKCU\Software\Classes\MarkdownReader.md\shell\open\command"
```

### 什麼時候需要重跑 install_association.py

登錄檔記的是**路徑**，不是檔案內容或版本，所以：

| 情況 | 要不要重新註冊 |
|---|---|
| 改程式、重新編譯到同一路徑 | **不用** |
| 執行檔大小或時間戳改變 | 不用 |
| `--clean` 清掉 `build/` | 不用 |
| 換打包方式（單一 exe ↔ 資料夾版） | **要**，路徑變了 |
| 搬移或更名 `dist/` 底下的檔案 | **要** |
| 換了應用程式圖示 | 不用，但檔案總管可能顯示舊圖示；重跑一次會呼叫 `SHChangeNotify` 刷新 |

若關聯指向的檔案被刪掉或搬走，雙擊 `.md` 會跳出「找不到應用程式」。重新編譯回原
路徑即可恢復，不需要重新註冊。

### 編譯瞬間的短暫空窗

`build.ps1 -OneDir` 會先清掉整個 `dist\MarkdownReader-onedir\` 再重建，那幾秒內
關聯指向的檔案並不存在。一般不會撞上，但如果剛好在編譯途中雙擊 `.md` 而失敗，
等編譯完成後重試即可。

### 兩條設計規範

1. **圖示一律來自 SVG 檔或 QPainter**
   `assets/icons/*.svg` 的 `stroke`/`fill` 寫成 `{color}` 佔位符，載入時置換成主題色後交給 `QSvgRenderer` 繪製，因此同一份向量圖能隨主題變色。程式中不使用任何 Unicode 字元或 Emoji 充當圖示。唯一的例外是任務清單的核取方塊——Qt 會直接丟棄 `<input type="checkbox">`，所以改由 `QPainter` 即時繪製成行內圖片。

2. **樣式集中在 `styles.py`**
   全專案只有 **一次** `setStyleSheet()` 呼叫（`viewer.MarkdownViewer.apply_theme`），套用 `styles.build_qss(theme)` 產生的單一字串，再靠 `objectName` 選擇器級聯到所有子元件；文件樣式則由 `setDefaultStyleSheet()` 套用 `styles.build_doc_css(theme, 字級)`。切換主題時，視窗外觀、內文排版、圖示顏色與程式碼高亮會一次同步。

## Qt rich text 的限制與對應作法

選用 `QTextBrowser` 而非 `QWebEngineView`，可讓 exe 少約 150MB 且啟動更快，代價是只支援 CSS 2.1 子集。以下是實測結果與本專案的處理方式：

| Qt 的實際行為 | 對應作法 |
|---|---|
| 區塊元素（`blockquote`/`pre`/`hr`/`h1`）的 `border`、`padding` **完全無效** | 由 `qt_html.py` 的 markdown 擴充改寫成單格表格，靠儲存格的 `border-left` / `padding` 呈現 |
| 只有表格儲存格的 `border`/`padding`/`background` 有效 | 引用區塊、程式碼區塊、標題底線全部走表格 |
| `<pre>` 若設 `background-color: transparent`，會把所在儲存格的底色整片蓋掉 | 明確填入與儲存格相同的顏色 |
| `h1`～`h5` 忽略所有 `font-size` 單位，固定使用內建比例 2.0 / 1.5 / 1.2 / 1.0 / 0.8 | 沿用內建比例；`h6` 是唯一吃 `pt` 的標題，明確指定字級避免階層反轉 |
| 段落行高倍率會套用到圖片所在的行框，圖片下方多出大片空白 | 只含一張圖片的段落改用 100% 行高 |
| `<input type="checkbox">` 會被丟棄 | 改用 `QPainter` 繪製的行內圖片 |
| 無邊框視窗的邊緣縮放判定會蓋掉右側捲軸 | 游標落在捲軸上時，縮放感應寬度縮到 4px，其餘讓給捲軸拖曳 |
| 圖片不會自動縮到視窗寬度，且會保留原始高度 | 覆寫 `loadResource()` 在載入時等比縮小；視窗寬度改變後重繪 |
| 字級要能隨縮放等比變化 | 文件 CSS 一律用 `em` / `%`（`px` 不會跟著縮放） |

## 已知限制

- 不支援圓角、陰影、Mermaid 圖表、HTML `<details>` 與 GFM 警示區塊（`> [!NOTE]`）。若日後需要完整保真度，唯一解是改用 `QWebEngineView`（exe 會增加約 150MB）；渲染層已隔離在 `document.py` 與 `viewer.py`，替換成本不高。
- 無邊框視窗不支援 Windows 11 的 Snap Layouts（滑鼠停在最大化鈕上跳出的版面選單），那需要攔截原生 `WM_NCHITTEST` 訊息。
- 「還原上次分頁」在多視窗下只記住最後關閉的那個視窗（每個視窗關閉時都會覆寫同一份紀錄，最後寫的贏）。要完整還原多個視窗需要另一套session 格式，目前不做。
- **還原成最大化之後，第一次點還原鈕沒有反應，要點第二次。**「一開始就以最大化
  顯示」的視窗沒有可回復的一般幾何，Qt 的 `showNormal()` 因此第一次不生效
  （純 Qt 的無邊框視窗也一樣，與本程式的實作無關）。可靠的修法是先以一般大小
  顯示、下一個事件回合才最大化，但那會讓每次啟動閃一下（實測約 114 ms），
  兩害相權之下維持現狀。
- 監聽端若正忙（例如正在跳確認對話框），轉交會等到逾時；資料仍在管道裡，對方有空就會讀到，只是分頁出現得慢一點。

## 疑難排解

| 狀況 | 處理方式 |
|---|---|
| **改了程式，雙擊開起來還是舊的** | 編到了另一個產物。確認關聯指向哪個版本，用對應的 `build.ps1` 或 `build.ps1 -OneDir`（見「改完程式之後的重新編譯流程」） |
| **編譯失敗 `PermissionError: [WinError 5]`** | 程式還開著，執行檔被鎖住。先 `taskkill /F /IM MarkdownReader.exe` 再編譯 |
| 雙擊 `.md` 跳「找不到應用程式」 | 關聯指向的檔案被刪掉或搬走了。重新編譯回原路徑即可，不需要重新註冊 |
| 編輯 `build.ps1` 後出現 parser error、中文變亂碼 | `.ps1` 必須存成 **UTF-8 with BOM**。PowerShell 5.1 讀沒有 BOM 的檔案會當成 ANSI（繁中系統為 cp950），中文會壞掉並讓字串沒有結尾 |
| 打包後圖示全部空白 | 確認打包指令有 `--add-data "assets;assets"` 與 `--hidden-import PyQt6.QtSvg` |
| 程式沒有畫面就消失 | 查看 `%LOCALAPPDATA%\MarkdownReader\error.log`，未攔截的例外都會寫在這裡 |
| 雙擊 `.md` 仍由其他程式開啟 | Windows UserChoice 優先，請用「開啟檔案 → 選擇其他應用程式 → 一律使用此應用程式」指定一次 |
| 中文顯示成亂碼 | 狀態列會顯示實際判定的編碼；若標示為 `latin-1（可能不正確）`，代表該檔案編碼超出偵測範圍 |
| 程式碼區塊沒有高亮 | 確認已安裝 `Pygments`（`py -3.13 -m pip install Pygments`） |
| 關掉程式後雙擊 `.md` 沒有反應、或新開的視窗立刻消失 | 單一 exe 的**本體行程**可能還活著佔著管道（用工作管理員砍掉啟動器不會連本體一起砍）。`taskkill /F /IM MarkdownReader.exe` 會一次清乾淨 |
| 雙擊 `.md` 開了新視窗而不是新分頁 | 兩個視窗來自**不同路徑**的執行檔（例如單一 exe 與資料夾版各開一個）時，各自都會是「第一個實例」。統一用同一個產物即可 |
| 雙擊 `.md` 後分頁出現但內容空白 | 這是收方在資料進緩衝區前就判定連線結束。若自行改過 `app/single_instance.py`，確認 `_on_connection` 補讀那段還在 |
